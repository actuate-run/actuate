Approve and Reject buttons in chat: the runtime and provider contract they run on.

- **sdk:** `ApprovalPrompt.buttons?: { route, nonce }` is set on approval notifications (never questions) when the runtime made a button nonce, for providers that render buttons. `ApprovalResult.via` gains `"chat"`, with a verified `by`: `<channel>:<user id>`, plus ` (<display name>)` when the provider gives one (the ID is checked by the provider's signature, the name is whatever the person set). New types for provider adapters and runtimes: `ProviderReply`, `ButtonActor`, `ButtonClick`, `ClickOutcome` and `ProviderInteractions`.
- **sdk:** `notify` on `waitForApproval` and `waitForInput` also takes `{ to, channel }` (new `Notify` type), which sends through that messaging channel when several are configured. `"owner"` stays a reserved string, and `{ to: "owner" }` is refused, like any malformed `notify`: the call throws. A channel that isn't configured is logged on the run as a delivery error, and the step still waits.
- **providers:** `ProviderDefinition` gains the optional `parseInteraction`, `isApprover`, `respondInteraction` and `routeHint` for chat providers that take button clicks. The contract has the one implementation of the button payload, `encodeButtonPayload` / `parseButtonPayload` (`ap1:<route>:<nonce>:<a|r>`, strict, at most 47 bytes, within Telegram's 64), and shared helpers: `parseApprovers` / `isListedApprover` / `formatApprovers` / `approversCredentialField` for an `approvers` credential (IDs separated by spaces or commas, `role:<id>` where the provider has roles), `clickOutcomeText`, `withoutLinkLines` and `decidedMessageText` for what the clicker sees, and `jsonReply` / `textReply`. `providerInteractions(definition, credentials)` and `providerInteractionsFromEnv(env, kind)` bind a provider's click handling for a runtime. An approver list restricts buttons only: the signed links stay in every message and still work for whoever holds them.
- **runtime:** a new `_actuate_approval_buttons` table (existing databases get it the first time a `RunManager` opens them) holds one random 96-bit nonce per approval that notifies someone, when `RunManagerOptions.buttonRoute` is set (`"local"` self-hosted, `LOCAL_BUTTON_ROUTE`). The nonce goes to the notifier as `ApprovalRequest.buttons` and nowhere else: not in run logs (a notifier error that quotes it has it replaced by `[nonce]`), step outputs, receipts or anything a run token reads, and actuator code can neither send `approval` (the runtime drops it) nor read the table. `ApprovalRequest.channel` carries `notify`'s channel. `pruneRuns` removes a run's nonces with it, and expired ones.
- **runtime:** new `RunManager.decideByButton(nonce, action, { by })`: synchronous, it checks the nonce, its expiry and that the step still waits, marks the nonce used and completes the wait (`{ approved, at, by, via: "chat" }`), then sets the run due and calls `scheduleWake`, so the pass runs from the alarm and never delays the provider's reply. It returns `decided`, `already` (a second or racing click, or a step decided by a link or the dashboard, with that decision), `expired` or `unknown`. New `chatApproverLabel`, `newButtonNonce`, `isButtonRoute`, `isButtonNonce`, `notifyTarget` and the `ButtonDecision` type.
- **runtime:** `createRuntime` takes `providerInteractions: (kind, env) => ProviderInteractions | null`. `POST /providers/:kind/webhook` asks the provider's `parseInteraction` first: a reply goes back verbatim; a click is checked for the `"local"` route and the approver list, decided, answered with `respondInteraction`, and its follow-up runs in `waitUntil`; anything else falls through to `providerWebhook`, whose `{ reply }` may now be a `ProviderReply` (status, content type, body) as well as a string.
- **providers:** the custom webhook's receiver can decide approvals. With a signing secret, an approval's standard body gains `approval.decide: { approve, reject, url }` (two `ap1:` payloads and the Reply URL), and templates gain `{{approvePayload}}` / `{{rejectPayload}}` (empty otherwise); the links stay. The receiver POSTs `{ "decision": "<payload>", "by": { "id", "name"? } }` to the Reply URL with the reply auth (Bearer secret or Standard Webhooks signature), and gets JSON back: `{ status, decision?, by?, at?, message }` (`decided`, `already`, `expired`, `unknown`, `not-approver`, `foreign`), or 400 `{ "status": "invalid", message }` for a bad payload or `by` (`id` 1-128 characters, no spaces or commas; `name` at most 128). The run resumes with `via: "chat"` and `by: "custom-webhook:<id> (<name>)"`. `by` is asserted by the receiver: Actuate verifies the secret, not the person. New optional credential `approvers` (`CUSTOM_WEBHOOK_APPROVERS`): the `by.id` values allowed to decide this way. A body without `decision` is still an ordinary reply.
- **cli:** `actuate dev` wires `providerInteractionsFromEnv`, so a chat provider configured in `.dev.vars` takes button clicks on its webhook.
