Approve and Reject buttons in Telegram, Slack and Discord, approvals decided by a custom webhook's receiver, and the runtime and provider contract they run on.

- **sdk:** `ApprovalPrompt.buttons?: { route, nonce }` is set on approval notifications (never questions) when the runtime made a button nonce, for providers that render buttons. `ApprovalResult.via` gains `"chat"`, with a verified `by`: `<channel>:<user id>`, plus ` (<display name>)` when the provider gives one (the ID is checked by the provider's signature, the name is whatever the person set). New types for provider adapters and runtimes: `ProviderReply`, `ButtonActor`, `ButtonClick`, `ClickOutcome` and `ProviderInteractions`.
- **sdk:** `notify` on `waitForApproval` and `waitForInput` also takes `{ to, channel }` (new `Notify` type), which sends through that messaging channel when several are configured. `"owner"` stays a reserved string, and `{ to: "owner" }` is refused, like any malformed `notify`: the call throws. A named channel that isn't configured always fails delivery, even when only one provider is configured: it is logged on the run as a delivery error, and the step still waits. **Behaviour change:** the same goes for `ctx.messaging.send(to, text, { channel })`, which used to send through the only configured provider whatever `channel` said, and now rejects, so a recipient meant for one channel never goes out through another.
- **providers:** `ProviderDefinition` gains the optional `parseInteraction`, `isApprover`, `respondInteraction` and `routeHint` for chat providers that take button clicks; a provider takes clicks only with the first three. The contract has the one implementation of the button payload, `encodeButtonPayload` / `parseButtonPayload` (`ap1:<route>:<nonce>:<a|r>`, strict, at most 47 bytes, within Telegram's 64), and shared helpers: `parseApprovers` / `isListedApprover` / `formatApprovers` / `approversCredentialField` for an `approvers` credential (IDs separated by spaces or commas, `role:<id>` where the provider has roles), `clickOutcomeText`, `withoutLinkLines` and `decidedMessageText` for what the clicker sees, and `jsonReply` / `textReply`. `providerInteractions(definition, credentials)` and `providerInteractionsFromEnv(env, kind)` bind a provider's click handling for a runtime. An approver list restricts buttons only: the signed links stay in every message and still work for whoever holds them.
- **runtime:** a new `_actuate_approval_buttons` table (existing databases get it the first time a `RunManager` opens them) holds one random 96-bit nonce per approval that notifies someone (not `notify: "owner"`), when `RunManagerOptions.buttonRoute` is set (`"local"` self-hosted, `LOCAL_BUTTON_ROUTE`). The nonce goes to the notifier as `ApprovalRequest.buttons` and nowhere else: not in run logs (a notifier error that quotes it has it replaced by `[nonce]`), step outputs, receipts or anything a run token reads, and actuator code can neither send `approval` (the runtime drops it) nor read the table. `ApprovalRequest.channel` carries `notify`'s channel. `pruneRuns` removes a run's nonces with it, and expired ones.
- **runtime:** new `RunManager.decideByButton(nonce, action, { by })`: synchronous, it checks the nonce, its expiry and that the step still waits, marks the nonce used and completes the wait (`{ approved, at, by, via: "chat" }`), then sets the run due and calls `scheduleWake`, so the pass runs from the alarm and never delays the provider's reply. It returns `decided`, `already` (a second or racing click, or a step decided by a link or the dashboard, with that decision), `expired` or `unknown`. New `chatApproverLabel`, `newButtonNonce`, `isButtonRoute`, `isButtonNonce`, `notifyTarget` and the `ButtonDecision` type.
- **runtime:** `createRuntime` takes `providerInteractions: (kind, env) => ProviderInteractions | null`. `POST /providers/:kind/webhook` asks the provider's `parseInteraction` first: a reply goes back verbatim; a click is checked for the `"local"` route and the approver list, decided, answered with `respondInteraction`, and its follow-up runs in `waitUntil` (if `respondInteraction` throws once the click is decided, the answer is an empty 200 and the decision stands); anything else falls through to `providerWebhook`, whose `{ reply }` may now be a `ProviderReply` (status, content type, body) as well as a string.
- **providers:** the custom webhook's receiver can decide approvals. With a signing secret, an approval's standard body gains `approval.decide: { approve, reject, url }` (two `ap1:` payloads and the Reply URL), and templates gain `{{approvePayload}}` / `{{rejectPayload}}` (empty otherwise); the links stay. The receiver POSTs `{ "decision": "<payload>", "by": { "id", "name"? } }` to the Reply URL with the reply auth (Bearer secret or Standard Webhooks signature), and gets JSON back: `{ status, decision?, by?, at?, message }` (`decided`, `already`, `expired`, `unknown`, `not-approver`, `foreign`), or 400 `{ "status": "invalid", message }` for a bad payload or `by` (`id` 1-64 characters, no spaces or commas; `name` at most 60, so `ApprovalResult.by` holds both uncut). The run resumes with `via: "chat"` and `by: "custom-webhook:<id> (<name>)"`. `by` is asserted by the receiver: Actuate verifies the secret, not the person. New optional credential `approvers` (`CUSTOM_WEBHOOK_APPROVERS`): the `by.id` values allowed to decide this way. A body without `decision` is still an ordinary reply.
- **providers:** Telegram approval buttons. With `webhookSecretToken` and a button nonce, approvals get Approve and Reject callback buttons; otherwise URL buttons to the confirm pages (only for `http(s)` links on a public host, so not under `actuate dev` on `localhost`), and questions get an Answer URL button. The text keeps its links. Clicks arrive on the bot's webhook, checked against `X-Telegram-Bot-Api-Secret-Token` (401 otherwise), and are answered in the webhook response with `answerCallbackQuery`; a deciding click then edits the message with `editMessageText` (links and buttons removed, "Approved by … at 14:02 UTC"). Other callback queries get a bare `answerCallbackQuery`. New optional credential `approvers` (`TELEGRAM_APPROVERS`): numeric user IDs. Self-hosted, register the webhook at the actuator's `/providers/telegram/webhook` with `secret_token` and `allowed_updates=["message","callback_query"]`.
- **providers:** Slack approval buttons. Approvals and questions go out as Block Kit, with `text` (links included) as the fallback. With the new optional `signingSecret` (`SLACK_SIGNING_SECRET`) and a button nonce, Approve and Reject are interactive; otherwise they are URL buttons to the confirm pages, and questions get an Answer URL button. Clicks are verified by `X-Slack-Signature` (v0 HMAC-SHA256, 5-minute window, 401 otherwise) and answered with an empty 200; a follow-up to the click's `response_url` then replaces the message for a decision (links and buttons removed) or posts an ephemeral note to the clicker. New optional credential `approvers` (`SLACK_APPROVERS`): member IDs. Self-hosted, set the app's Interactivity Request URL to the actuator's `/providers/slack/webhook`.
- **providers:** Discord approval buttons. With a bot token and the new optional `publicKey` (`DISCORD_PUBLIC_KEY`, the application's public key), approvals get interactive Approve and Reject buttons; otherwise (no public key, or a channel webhook) link buttons to the confirm pages when every link is at most 512 characters, else text only, and questions get an Answer link button under the same rule. Interactions are verified by Ed25519 `X-Signature-Ed25519` (WebCrypto, 5-minute window, 401 otherwise), a PING gets its PONG, and a click is answered with type 7 (`UPDATE_MESSAGE`, links and buttons removed) for a decision or an ephemeral type 4 otherwise; other interactions of the application get a polite ephemeral reply. New optional credential `approvers` (`DISCORD_APPROVERS`): user IDs and `role:<id>` entries. Self-hosted, set the application's Interactions Endpoint URL to the actuator's `/providers/discord/webhook`.
- **providers:** `parseProviderWebhookFromEnv` returns null (so `{ ignored: true }`) for a configured provider that takes no webhooks of its own, such as Slack and Discord, instead of a 401; a provider that isn't configured is still a 401.
- **cli:** `actuate dev` wires `providerInteractionsFromEnv`, so a chat provider configured in `.dev.vars` takes button clicks on its webhook.
